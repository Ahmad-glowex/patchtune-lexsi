# PatchTune-mini: Teaching Tiny Aya Global to Make Reliable Tool Calls

**Lexsi AI Safety & Alignment Hackathon — Track 3: Agentic Fine-tuning (AgentTune + AuditKIT)**
**Problem statements:** #1 Reliable tool calling (primary) · #2 Efficient trajectories (secondary)
**Author:** Tashfiq Ahmad (solo) — HF: [Tashfiq99](https://huggingface.co/Tashfiq99) · GitHub: [Ahmad-glowex](https://github.com/Ahmad-glowex)

---

## 1. Problem statement & approach in brief

Coding agents fail in a mundane way: not because they cannot write code, but because they call their tools badly — the wrong tool, malformed arguments, the right calls in the wrong order, or loops that never reach a verified fix. Problem Statement #1 of this track asks for exactly that failure mode to be trained away with reinforcement learning on real tool-calling rollouts, and Problem Statement #2 asks that trajectories become efficient — fewer redundant or looping calls — without lowering success.

**PatchTune-mini** post-trains `CohereLabs/tiny-aya-global` (3.35B, dense, open-weights) with GRPO so that it performs one complete, verifiable coding-agent workflow: given a natural-language bug report against a small Python package, the agent must

1. `search_code` — locate the buggy code,
2. `read_file` — read the implicated file,
3. `apply_patch` — apply a unified-diff fix,
4. `run_tests` — verify the fix against the package's test suite,

in that canonical order, with well-formed arguments, ending in an outcome that is *verified by the tests themselves*, not judged by another model. Every training task is a fresh instance of a tiny Python package (`tinylib`) with exactly one planted single-line bug drawn from 8 bug families, a failing unit-test suite before the fix, and a passing suite after the canonical fix. Because success is programmatically checkable end-to-end, the reward signal is grounded: format, order, and outcome are scored separately, and the largest reward component is paid only when the sandbox test suite actually passes.

## 2. Hackathon repos used

This project chains the two Track 3 toolkits, AgentTune and AuditKIT, into one pipeline:

- **AgentTune (Lexsi Labs)** — the training framework and design source. AgentTune's own documentation states that its `core/sft` path is broken end-to-end and that agentic RL (GRPO) is the training path that runs; we therefore built GRPO-only. Two pieces of AgentTune directly shaped this project:
  - Its **GRPO training design and conventions**, including the documented warning that reward functions receive *flattened completion strings* rather than message dicts — our reward parser (`patchtune/reward.py`) is written defensively against exactly that convention, accepting dicts, JSON strings, JSON-lines, and `tool(arg=...)` text lines, and never raising.
  - Its **reward-design guidance for tool-calling agents**, which our reward function implements: positive reward for the correct tool with well-formed arguments, a bonus for correct ordering, the main bonus for the verified final outcome, and penalties for malformed calls, loops, and excess calls.
  - Training itself was executed through AgentTune's TRL-based GRPO path (the TRL `GRPOTrainer` backend), because that is the path that runs end-to-end with a LoRA adapter on a 3.35B model in free-tier GPU memory (see §7 for what else was tested).
- **AuditKIT (Lexsi Labs)** — the evaluation framework. AuditKIT's agent scorers define the evaluation vocabulary used for the before/after comparison in §8: task success, tool-call accuracy, calls per task (the efficiency metric for Problem Statement #2), and malformed-call rate, computed over the same held-out traces for the base and tuned models.

## 4. Datasets and benchmarks used and their licences

All data is synthetic and was generated by this project's own generator (`toyrepo/` + `patchtune/tasks.py`) during the hackathon. No third-party dataset was used.

| Artifact | Contents | Licence |
|---|---|---|
| `Tashfiq99/patchtune-mini-data` — train split | 150 synthetic tasks: bug report, buggy repo file map, canonical tool sequence, canonical fix diff | MIT |
| `Tashfiq99/patchtune-mini-data` — held-out split | 50 tasks in the identical format, used only for evaluation | MIT |
| Held-out benchmark | The same 50 held-out tasks, run interactively against base and tuned models | MIT |

Train and held-out splits are deliberately hard to memorise across: they use **disjoint module-name pools and disjoint instruction phrasings**, so a held-out score reflects generalisation to unseen surface forms, not recall of training templates. Each task's ground truth is executable: the planted bug makes the suite fail, the canonical patch makes it pass, and both directions are asserted by the project's unit tests.

## 7. Experiments run, findings, and what else was tested

**Environment and harness (verified before any GPU work).** The sandbox tool executor (`search_code`, `read_file`, `apply_patch`, `run_tests`), the task generator, the reward function, and the 4-metric evaluation harness were built and unit-tested first: 21/21 tests pass, covering every bug family (fails pre-fix, passes post-fix), malformed/path-escape/bad-patch handling in the tools, reward parsing of flattened-string completions, and train/held-out disjointness. One real bug was found and fixed during this phase: planted fixes are same-length one-line edits, so a patched file can share size and mtime with the buggy original and Python would execute stale `__pycache__` bytecode — the executor now clears `__pycache__` after patching and before every test run.

**Training configuration (the run reported here).** GRPO with a LoRA adapter on the 4-bit (bitsandbytes) base model, on a single T4 GPU: 25 optimizer steps, batch 2 × 2 generations per step, maximum completion length 512 tokens. Reward = matched expected calls (tool + arguments + order) + verified-outcome bonus (paid only when the sandbox suite passes), with penalties for malformed calls, loops, and excess calls.

**What else was tested.**
- *Larger batches/generations (batch 4 × 4 generations):* reward variance within groups was healthy, but the configuration exceeded T4 memory partway through the run; the reported run uses the smaller, stable configuration above.
- *Smoke configuration (5 steps, shorter completions):* verified the full loop — rollout, reward, checkpointing, adapter save — end-to-end before committing to the real run.
- *Mock-model harness runs:* deterministic scripted agents (a sloppy "base" and a perfect "tuned") were run through the identical evaluation code first, confirming the harness produces sensible before/after separation (mock-base 0.50 success → mock-tuned 1.00) before any real model was evaluated. These are pipeline sanity checks only, not results.

**Findings so far.** The base model is a weak tool-caller out of the box (§8): it solves none of the 50 held-out tasks, produces a high rate of malformed calls, and typically stops after ~2.7 calls per task — short of the 4-call canonical trajectory — so most trajectories die before reaching a verifiable fix. This confirms the premise of Problem Statement #1 for this model class: the failure is in tool-use behaviour, and it is measurable. After tuning, the picture splits. On format-level metrics the adapter improves on the base model: tool-call accuracy rises from 0.125 to 0.217 (23 of 106 calls matched the expected tool, arguments and position), the malformed rate falls from 1.8235 to 1.5283, and calls per task drop from 2.72 to 2.12 — the tuned model wastes fewer turns. But the headline metric does not move: task success stays at 0.0. No held-out task was solved end-to-end by either model. Per-chunk results vary widely (the first 10 tasks are the worst — malformed rate 6.56, accuracy 0.11, and in 7 of those 10 tasks the tuned model produced no valid call at all — while later chunks are visibly cleaner), which suggests the adapter learned the call format unevenly rather than the full four-step trajectory: matched calls are still too few, in the wrong places, or followed by a break before a verified fix.

## 8. With more credits: approach, and before/after results

**Approach recap.** Same task, same data, same harness, before and after: the base model and the GRPO-tuned adapter were each run interactively on the identical 50 held-out tasks — generation interleaved with real tool execution in a per-task sandbox — and scored with the same four AuditKIT-style metrics.

**Results (held-out, 50 tasks):**

| Model | Task success rate | Tool-call accuracy | Avg calls / task | Malformed rate |
|---|---|---|---|---|
| Base — `CohereLabs/tiny-aya-global` | 0.0 | 0.125 | 2.72 | 1.8235 |
| Tuned — PatchTune-mini adapter | 0.0 | 0.217 | 2.12 | 1.5283 |

**Interpretation.** Read plainly, this is a negative result on the headline metric with real movement underneath it. GRPO at this scale — 25 short steps, batch 2 × 2 generations, completions capped at 512 tokens, mean reward still negative and 5 of 25 steps with zero within-group variance — was enough to teach the *shape* of tool calling (better-formed calls, fewer malformed outputs, a higher per-call match rate) but not enough to carry a trajectory through search → read → patch → test to a verified pass. That is consistent with the training read: the learning signal existed but was thin, and the outcome bonus was rarely reachable inside the length cap. What the run does establish is the pipeline itself: synthetic verifiable tasks → GRPO post-training with checkpointed, resumable runs → an identical interactive evaluation harness before and after, with every artifact public. The binding constraint in this experiment was the training budget, not the harness — which is exactly what §8's "with more credits" list is aimed at.

**Limitations (honest).** This is a small, deliberately narrow experiment, and its numbers should be read that way. Training was short — 25 GRPO steps at batch 2 × 2 generations is enough to move behaviour, not to converge; a longer run with more generations per step (which gives GRPO a richer within-group comparison) is the obvious next step. During training, completions frequently hit the 512-token length cap, which truncates some trajectories before they can finish and caps the outcome reward they can earn. The task distribution is synthetic and small — 8 single-line bug families in one toy package — so results demonstrate the training method on a verifiable micro-domain; they do not by themselves establish transfer to real repositories, multi-file bugs, or open-ended instructions. Held-out scores are protected from template memorisation by disjoint module names and phrasings, but the underlying bug families are shared between the splits.

**With more credits, we would:** (i) scale to several hundred GRPO steps with 4–8 generations per step on a larger GPU, so every step carries a stronger learning signal; (ii) raise the completion cap and add an explicit reward term for terminating cleanly after `run_tests` passes, attacking the length-cap truncation directly; (iii) widen the task distribution — more bug families, multi-line and multi-file bugs, and a second toy package — and re-measure transfer; (iv) run the full AuditKIT scorer suite over all rollout traces and publish the traces alongside the metrics.
